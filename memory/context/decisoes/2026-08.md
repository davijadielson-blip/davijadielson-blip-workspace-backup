## 2026-08-08 - Correção de acesso Google Drive via gog para subagentes

Jadielson reportou no tópico LÓGIKA que subagentes estavam com dificuldade para acessar o Google Drive.

Diagnóstico:

- O caminho oficial do Google no ecossistema continua sendo `gog`, não Zapier.
- O ambiente de sessão estava herdando `GOG_KEYRING_PASSWORD=SUA_SENHA_FORTE_AQUI`, valor placeholder vindo de `/data/.openclaw/.env`.
- Com esse placeholder, o keyring file-based do `gog` falhava com `aes.KeyUnwrap(): integrity check failed`.
- Ao carregar o segredo correto via `scripts/gog-auth.sh`, as contas `logikacreative.mkt@gmail.com` e `loh.open.logika@gmail.com` autenticaram e fizeram refresh com sucesso.
- A conta pessoal `davijadielson@gmail.com` ainda mantém um token antigo/corrompido no cliente `openclaw`, exigindo reautorização ou limpeza assistida posterior.

Correções aplicadas:

- Removido o placeholder do `/data/.openclaw/.env` e persistido o valor correto a partir do arquivo secreto local, sem expor o segredo no Cofre.
- Criado wrapper seguro em `/data/.local/bin/gog` para carregar `/data/.openclaw/credentials/gog/keyring-password` antes de chamar o binário real do `gog`.
- Preservado o symlink anterior como `/data/.local/bin/gog.real-link`.

Validação:

- `gog auth doctor --check` confirmou keyring aberto, 2 tokens legíveis de 3 e refresh bem-sucedido para `logikacreative.mkt@gmail.com` e `loh.open.logika@gmail.com`.
- Busca real no Drive profissional `logikacreative.mkt@gmail.com` retornou arquivos recentes com sucesso.

Regra operacional:

- Subagentes devem usar sempre `gog --account <conta> ...` com conta explícita.
- Para frentes profissionais da LÓGIKA/Saúde, usar prioritariamente `logikacreative.mkt@gmail.com`.
- A conta pessoal `davijadielson@gmail.com` não deve ser prometida como disponível até reautenticação/limpeza assistida do token `openclaw`.

## 2026-08-09 - Recuperação do gog pessoal davijadielson

Jadielson autorizou resolver o acesso `gog` da conta pessoal `davijadielson@gmail.com`.

Diagnóstico:

- O token ativo da conta pessoal no cliente `openclaw` estava ilegível com `aes.KeyUnwrap(): integrity check failed`.
- O cliente `default` tinha backup local legível em `/data/.local/share/gogcli/keyring-backup-20260808-050337`.
- Teste isolado desse backup confirmou `gog auth doctor --check` com refresh bem-sucedido e busca real no Drive pessoal.

Correção aplicada:

- Os arquivos corrompidos do cliente `openclaw` para `davijadielson@gmail.com` foram movidos para quarentena em `/data/.openclaw/quarantine/gog-personal-openclaw-corrupt-2026-08-09/`, sem exclusão definitiva.
- O token pessoal legível do cliente `default` foi restaurado do backup local para o keyring ativo.
- `scripts/gog-auth.sh` passou a usar `default` como cliente padrão e `GOG_PERSONAL_CLIENT=default` para a conta pessoal.

Validação:

- `gog auth doctor --check` passou sem erro, com refresh bem-sucedido para `davijadielson@gmail.com`, `logikacreative.mkt@gmail.com` e `loh.open.logika@gmail.com`.
- `gog_drive pessoal search "trashed=false" --max 3` retornou arquivos reais do Drive pessoal.
- `gog_drive logika search "trashed=false" --max 1` continuou funcionando.

Regra operacional:

- Para a conta pessoal, usar `gog_drive pessoal`, `gog_calendar pessoal`, `gog_docs pessoal` ou `gog --account davijadielson@gmail.com --client default ...`.
- Manter o cliente `openclaw` pessoal em quarentena ate decisao futura; nao tentar usa-lo como padrao.
